Prepare a fire-and-forget "overnight cleanup" mega-epic of 20-30 single-bound, parallel-safe sub-tickets that the watcher daemon can chew through unattended overnight.

**Design philosophy:** maximize independent throughput, accept losses. Single-ticket failures are expected; the morning workflow is `/close-epic` → epic→main PR with whatever subset succeeded. There is no rescue path. Tickets are independent by construction (no `blocked_by` chains; one file per ticket).

**Two operator gates:**
- **Gate 1 (Phase 5)** — review candidate list before any Linear or git writes
- **Gate 2 (Phase 8)** — final launch confirmation before the watcher dispatches

Either gate can abort cleanly.

Arguments: `$ARGUMENTS` may include `--target-count N` (default 25), `--epic-title "..."`, `--dry-run` (print everything but skip Linear writes + manifest writes).

### Phase 0 — File-size auto-tickets (new)

Scan for files over the RECOMMEND threshold and queue them for splitting.

```bash
# Production files over RECOMMEND (700)
find app scripts -name '*.py' -type f -not -name '__init__.py' \
  -exec wc -l {} + | sort -rn | awk '$1 >= 700 && $2 != "total"'

# Test files over RECOMMEND (1200)
find tests -name '*.py' -type f -not -name 'conftest.py' \
  -exec wc -l {} + | sort -rn | awk '$1 >= 1200 && $2 != "total"'
```

For each file in the result set:

**Skip if:**
- File is in the **TIER 1** forbidden list (see forbidden-files section)
- File has been touched in a commit in the last 7 days (`git log --since='7 days ago' --name-only | grep -q "<file>"`) — recent churn
- An open Linear ticket already targets this file (`list_issues` filtered to title-mentions)

**Otherwise queue a candidate** (the actual `save_issue` happens in Phase 6 alongside Sonar tickets):

```
title:    "Split <file> (<LOC> LOC over <RECOMMEND/BLOCK> threshold)"
labels:   ["Local-ready", "Refactor", "Infra"]
priority: 4
state:    Groomed (will set after parent epic exists)
source:   "filesize"
metadata: { file: <path>, current_loc: <N>, threshold: <T>, sections: [...] }
```

**Auto-extracted sections** (used in the description body):

```bash
grep -n '^# -\{3,\}' <file> | head -40
# These produce the suggested-split structure for the AC.
```

**Description template** (rendered into the ticket body in Phase 6):

```
## Goal

Split `<file>` (currently <LOC> LOC, over the <production|test> RECOMMEND
threshold of <RECOMMEND>) into themed sibling files. Pure mechanical
refactor — no test renamed/removed/modified; no source semantics changed.

## Section dividers (auto-extracted)

<line numbers + section headers from `# ---` markers>

## Suggested split

Group sections by topic into 3-5 themed sibling files; each new file
under the RECOMMEND threshold.

## Allowed paths

- `<file>`
- For source: matching `tests/test_<stem>*.py`
- For test: sibling `tests/test_<stem>*.py` glob

## Acceptance criteria

- All existing tests still pass (no rename, removal, modification)
- Each new file in the family is under RECOMMEND
- ruff check . / mypy app/ / pytest / lint-imports all pass
- No behavior change

## Why P4 Low

Auto-generated by /prepare-overnight-epic. Bounded scope, mechanical.
```

Phase 0 candidates merge into the same candidate pool as backlog + Sonar in Phase 1 / 4. They are subject to the same TIER 2 cap (see Phase 4) and same parallel-safety dedupe.

### Phase 1 — Mining (three sources, prefer backlog over Sonar)

#### Source A: existing Linear backlog (preferred)

Query in three passes — `Groomed`, `Todo`, and `Backlog`. Backlog tickets must pass an auto-promotion heuristic before being treated as candidates.

```
mcp__linear-server__list_issues(
    project: "{{ linear_project }}",
    state: "Groomed",   # then re-run with "Todo", then "Backlog"
    labels: "Local-ready",
    limit: 100,
)
```

For each result, fetch `get_issue(id, includeRelations: true)` to read parent epic + labels + full description.

**Auto-promotion heuristic (Backlog state only)**:

A `Backlog` ticket is auto-promotable to candidate iff ALL of:

- Description contains a `## Files`, `## Allowed paths`, or explicit `allowed_paths` block with concrete file paths.
- ≥2 acceptance criteria bullets (`- ` lines under an `## Acceptance criteria` or similar header).
- Description does NOT contain spike/judgment markers: regex `\b(spike|design|architect|decide|investigate|explore|research|evaluate|consider|discuss|propose)\b` (case-insensitive).
- No `Spike` label.
- Single-bound (no `blockedBy` relations).

Auto-promoted candidates get `save_issue(id, state: "Groomed")` + a comment "Auto-promoted by overnight epic skill — see WOR-380." If a Backlog ticket fails the heuristic, skip it silently.

**Filter to overnight-safe** (applies to all three states):

- Description contains a `## Files` or `allowed_paths` section with **1-3 files** total. Skip if larger.
- Parent epic is NOT in the active high-priority list:
  - `WOR-335` (Watcher resilience)
  - `WOR-300` (Watcher metrics correctness)
  - `WOR-298` (Routing redesign)
  - `WOR-365` (Metrics enrichment Wave 2 — closing)
  - or any epic whose title contains "Wave 1" or "Critical"
- No open PR or branch already exists for the ticket (check via `gh pr list --search <WOR-NNN>` — skip if any).
- Priority is **2 (High), 3 (Normal), or 4 (Low)**. Never include Urgent (1) — that needs supervised execution. (P2 is allowed as long as the ticket has clear AC; difficulty is OK, judgment-required is not.)

For each surviving backlog candidate, record:
- Existing parent epic (will be replaced by the mega epic — operator can opt out per-ticket)
- Inferred file list from the description's `allowed_paths` block
- Whether it was auto-promoted from Backlog (flag for Phase 5 disclosure)

#### Source B: SonarQube findings (always included, target ~30-40% of final list)

**Always pull Sonar findings — do not skip even if backlog is full.** The mix is a stress-test variable: a 100% backlog batch gives less informative telemetry than a mixed batch. Target Sonar's share of the final list at **30-40%**; trim later in Phase 4.

Query:

```
mcp__sonarqube__issues(
    project_key: "virppa_repo-scaffold-desktop",
    severities: ["MAJOR", "MINOR"],
    statuses: ["OPEN", "CONFIRMED"],
    resolved: false,
    rules: [
        "python:S1172",   # unused parameter
        "python:S1481",   # unused local variable
        "python:S1854",   # dead store
        "python:S1143",   # unnecessary if/else
        "python:S125",    # commented-out code
        "python:S100",    # docstring naming convention
        "python:S5754",   # bare except clauses
    ],
    limit: 200,
    facets: ["files", "rules", "severities"],
)
```

**This rule list is the allow-list, not a starting point.** Add new rules ONLY after observing one overnight where they succeed without manual rescue.

For each Sonar finding, record:
- File path (`component` field)
- Rule ID + count
- Severity

### Phase 2 — Filter

Drop candidates where:

**Forbidden files** — see the 3-tier list at the bottom of this skill. Briefly:

- **TIER 1** (always forbidden — watcher hot path): `watcher.py`, `dispatch.py`, `watcher_finalize.py`, `watcher_helpers.py`, `watcher_subprocess.py`. Breakage mid-overnight kills the running watcher or its next reap cycle.
- **TIER 2** (conditionally allowed): `generator.py`, `manifest.py`, `metrics.py`, `escalation_policy.py`, `bench_store.py`. Allowed only if (a) the candidate's `change_type` is `refactor` or `docs`, AND (b) the title starts with "Split" or "Add tests for", AND (c) AC has no behavior changes. Tier 2 is also subject to a per-batch cap of **4** (see Phase 4).
- **TIER 3** (always allowed): everything else under `app/core/`, `app/cli.py`, `app/main.py`, plus `tests/test_*.py` for test additions and Phase-0 splits.

**Forbidden directories**:
- `app/ui/**` (PySide6, hard to test headlessly)
- `.claude/**` (don't touch skills/hooks)
- `tests/**` is conditionally allowed: TIER 3 splitters generated by Phase 0 may target test files; otherwise excluded.

**File-size cutoff**: any file > 700 LOC for production / > 1200 LOC for tests is excluded **unless the candidate's purpose is to SPLIT it** (Phase-0-generated tickets bypass this). Use `wc -l <file>`.

**Already-claimed**: any file that another open Linear ticket already targets (check via `list_issues` filtered to file path mentions). Avoid stomping on in-flight work.

**Hard cap**: if surviving candidates count > target_count × 1.2 (e.g. 30 for target 25), trim to target_count × 1.2 max before Phase 3.

### Phase 3 — Dedupe by file

**At most one ticket per file.** This eliminates file conflicts by construction — no two in-flight workers ever touch the same file.

For Sonar candidates, group findings by file. Multiple findings on `app/core/foo.py` become one ticket with title like:
> "Fix Sonar findings in foo.py: S1172 (3), S1481 (1)"

For backlog candidates, the existing ticket title is preserved.

If a backlog candidate AND a Sonar candidate target the same file, prefer the backlog candidate (already human-shaped).

---

### Phase 4 — Rank + variety floor + TIER 2 cap

Three-pass selection, in order:

#### 4a. Variety floor — guaranteed minimums in the final list

Before pure ranking, ensure:

- **≥5 backlog candidates** (if available)
- **≥5 Sonar candidates** (if available)
- **≥3 distinct parent epics** in the original-parent set (for backlog candidates), so the batch isn't all-WOR-NNN-children.
- **All Phase-0 file-size candidates** are kept up to the TIER 2 cap (see 4c). These are mostly TIER 3 (test files, cli.py, post_setup.py); only orchestration-file splits hit the TIER 2 cap.

If a category is short, top up from the most-promising remainder.

#### 4b. Within each category, sort by

1. **Source preference**: backlog → Phase-0 splits → Sonar.
2. **Within each source, fewer findings/files first** (smaller scope = faster, more reliable).
3. **Within ties, lower severity first** (MINOR before MAJOR).
4. **Within ties, smaller file LOC first**.

#### 4c. TIER 2 cap

Across the entire final list, allow at most **4** candidates whose `allowed_paths` touches a TIER 2 file (see 3-tier list at bottom). This bounds the blast radius if any one TIER 2 ticket breaks something.

If the variety floor + TIER 2 cap together undershoot `--target-count`, the list is shorter — that's OK. Quality over quantity.

Take top `--target-count` (default 25). Discard the rest.

### Phase 7 — Branch + manifest per sub-ticket

For each sub-ticket (both re-parented backlog and new Sonar):

**7a. Create the worker branch off the epic**:
```bash
git checkout <EPIC_BRANCH>
git pull origin <EPIC_BRANCH>
git checkout -b <sub-ticket-branch>
git push -u origin <sub-ticket-branch>
git checkout main
```

The sub-ticket branch name comes from Linear's `gitBranchName` field (e.g. `wor-242-tighten-typing-in-user_prefs`).

**7b. Pre-load context_snippets**:
For each file in `allowed_paths`, read the first 80 lines (cap at 3000 chars). These become the `context_snippets` field of the manifest — workers don't need to Read the file again.

If `allowed_paths` includes a `tests/test_<stem>*.py` glob, expand it to actual file paths via Glob first, then read each.

> **`linear_id` field:** All sub-tickets in this skill are Batch 1 (`status: "ReadyForLocal"`), so `linear_id: null` is correct — the watcher resolves the UUID at dispatch time. We never use `WaitingForDeps` because there are no dependency chains in fire-and-forget mode.

> **`allowed_paths` test glob**: per WOR-353, `tests/test_<stem>*.py` covers sibling test files automatically. Don't enumerate them — let the glob do it.

> **At this point, sub-tickets are still in `Groomed` Linear state.** The watcher only picks up `ReadyForLocal`, so nothing dispatches yet. Phase 8 is the explicit launch.

## First-run guidance

For the first overnight using this skill:
- Use `--target-count 5` (small batch to validate the flow)
- Run on a Friday afternoon — sleep on it; check `/close-epic` flow Saturday
- Morning retro should query the new metrics columns (per WOR-365):
  ```sql
  SELECT effort, outcome, COUNT(*), AVG(local_wall_time/60) AS avg_min
  FROM ticket_metrics WHERE epic_id = '<MEGA_EPIC>'
  GROUP BY effort, outcome;

  SELECT ticket_id, api_retry_count, dispatch_concurrency, tags
  FROM ticket_metrics WHERE epic_id = '<MEGA_EPIC>'
  ORDER BY local_wall_time DESC;
  ```
- Success threshold: ≥60% of attempted tickets land in main = skill is working. <40% = tighten the allow-list.
